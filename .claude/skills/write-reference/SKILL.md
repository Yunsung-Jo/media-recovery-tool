# 레퍼런스 문서 작성

**목적:** 외부 포맷·스펙·API 사실과 작업 중 확립한 포맷 사실을 모아, 다음 작업이 같은 것을 다시
조사·추측하지 않게 한다. 살아있는 문서. 절 구성은 `0000-template.md`, 문서 경계는
[doc-roles](../shared/doc-roles.md), 문체는 [doc-style](../shared/doc-style.md).

## 언제 쓰나

외부 스펙이 불확실해 찾아볼 때 / 아는 포맷 지식을 처음 문서화할 때 / 작업 중 실측한 포맷 사실을 보존할
때 / 기존 문서에 덧붙일 때. 포맷 사실은 **확립한 즉시** 적는다(리파인까지 미루지 않는다 — 브랜치와 무관한
참이라 즉시 안정적). off-target으로 발견한 포맷 사실도 백로그가 아니라 여기 바로.

## 두 축을 구분하라

작성 방식을 가르는 것은 **① 지식을 어디서 얻나(출처 모드)**와 **② 얼마나 믿을 수 있나(신뢰 등급)** —
서로 다른 축이다.

### 출처 모드 — 서브에이전트 위임 여부를 가른다

| 출처 | 작성 | 서브에이전트 |
|------|------|--------------|
| **외부 수집** (모른다 / 권위 필요) | 검색 후 작성 | **위임** (검색 노이즈 격리) |
| **아는 지식** | 메인에서 작성 + 검증 | 안 함 |
| **작업 중 실측** | 메인에서 작성 | **금지** |

**실측·아는 지식을 위임하지 마라.** 실측(방금 잰 오프셋·gray 값)은 이 작업 컨텍스트에만 있어 차갑게
시작하는 서브에이전트가 모른다 — 위임하면 잃는다. 아는 지식은 검색이 불필요. 단 **검증에 웹 검색이
필요하면 그건 외부 수집이다**(위임). 아는 지식의 검증은 로컬 코드(`carver/...`) 대조에 한한다.

### 신뢰 등급 — 본문에서 라벨로 구분

확실한 외부 사실·프로젝트 검증·추측이 섞이기 쉽다. 어디까지 믿어도 되는지 라벨로 드러낸다.

| 등급 | 무엇 | 표기 | 의무 |
|------|------|------|------|
| **확실** (외부 사실) | 스펙·RFC·표준의 보편 사실 | 링크(가능하면 조항 §) | 출처 링크 필수 (예: `ITU-T T.81 §F`) |
| **실측** (프로젝트 검증) | 이 데이터셋에서 잰 사실 | `(실측)` | 방법·표본; 보편 사실 아님(프로젝트 한정) |
| **미검증** (추측) | 아직 대조 못 한 모델 지식·가설 | `(미검증)` | 사실로 적지 않음; 검증하면 위로 승격 |

**모델 지식은 검증 전에 사실로 적지 않는다** — 권위 출처·코드와 대조한 뒤 '확실/실측'으로, 못 하면
`(미검증)`. 할루시네이션 위험이 가장 크다.

## 절차

1. **기존 확인** — 기존 문서가 이 사실을 **자연스럽게 담을 수 있으면** 절을 덧붙여 확장한다(억지로 담아
   비대·산만·초점 흐려지면 새 문서). 새 문서는 [공통 작성 절차](../shared/doc-roles.md), 파일명 `<주제>.md`.
2. **출처 모드대로** — 외부 수집은 위임(아래), 실측·아는 지식은 메인에서. **혼합**이면 외부 부분만 위임해
   파일을 만들게 하고, 반환 후 메인에서 실측 절을 `(실측)`으로 덧붙인다(흔하다, 예: `jpeg-markers`).
3. **핵심만** — 현재 작업에 필요한 절만(전체 스펙 복사 금지). 코드·다른 reference·ADR을 상호링크한다.

**외부 수집 위임**(외부 수집일 때만): `general-purpose` 서브에이전트에 맡겨 검색 노이즈를 메인에서
격리한다. 검색(WebSearch/WebFetch로 공식 문서·RFC 확인) → 핵심만 추출 → 파일 생성·README 갱신 → 생성
경로·담긴 내용·출처 링크를 한 단락으로 요약 반환. 메인은 요약만 받아 재개한다.

## 자가점검

- [ ] 세 등급(확실/실측/미검증)을 라벨로 구분하고, 모델 지식을 코드·출처로 검증해 검증한 출처로 표기했나?
- [ ] 인용한 포맷 사실(매직바이트·청크·조항)을 출처·표본과 대조했나?
